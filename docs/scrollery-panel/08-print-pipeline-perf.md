# Panel report — Performance & Output Pipeline

## Summary
The rendering architecture is sound and the seam work is genuinely good: `Scrollery_render.tpl` loads 19 KB of CSS and nothing else, `_filters.tpl` already documents the "define once per page" discipline, and `reload()` in `scrollery.js:345` uses a real `AbortController` so stale previews cannot win. The cost problem is entirely in the BYTES, not the logic. **All 253 art files are raw PNG/JPG, 50 of them exactly 2550x3300**; one certificate pulls ~3.8-4.6 MB, and nginx serves every byte with `Cache-Control: public, max-age=300, must-revalidate` (verified live against the running container). The largest risk is not the art but `window.print()` firing before webfonts resolve; the cheapest win is a build-time WebP pass measured at **42.4 MB -> 14.0 MB on the PNGs alone**.

## Findings

- **[BUG] Auto-print races the webfonts**
  - Now: `Scrollery_render.tpl:54` — `window.addEventListener('load', function(){ window.print(); });`. All five faces in `scrollery.css:24-62` are `font-display:block`, i.e. invisible-then-fallback after ~3s.
  - Proposal: `Promise.all([document.fonts.ready, new Promise(r=>addEventListener('load',r))]).then(()=>window.print())`, with a `setTimeout` failsafe so a font 404 still prints. Add `<link rel="preload" as="font" type="font/woff2" crossorigin>` for BlackChancery and Averia-Regular in the render head.
  - Why: the `load` event fires when the ~4 MB of art finishes; the 276 KB of fonts may land after. The failure is silent and total — the certificate prints in Times, or with blank text where `block` is still hiding glyphs. Nobody notices until it's on paper.
  - Effort: S — Risk: none; `document.fonts` is universal.

- **Art is cached for five minutes and has no fingerprint** (measured, not assumed)
  - Now: `nginx.ork3.config:65-67` — `location ~* \.(jpg|gif|png) { add_header Cache-Control "public, max-age=300, must-revalidate"; }`. Live check on `parchment.jpg`: that header, 1,690,225 bytes. The regex omits `jpeg`, `svg` and `webp`, so `squiggly-top.svg` comes back with **no `Cache-Control` at all**. CSS/JS get `?v=filemtime()` busting (`Scrollery_render.tpl:31`); art URLs get nothing.
  - Proposal: a `location ^~ /assets/scrolls/` block with `max-age=31536000, immutable`, plus `gzip_types image/svg+xml`. Art is immutable by construction; if a file ever changes, append `?v=` from a build manifest.
  - Why: every print run more than 5 minutes stale issues ~25 blocking conditional requests before the first pixel. Officers print in bursts on event day, from park wifi.
  - Effort: S — Risk: stale art after a redeploy — hence the manifest escape hatch.

- **WebP renditions: 62 MB -> ~33 MB, and 4 MB/cert -> ~1.6 MB** (measured with ImageMagick on this corpus)
  - Now: 222 PNG (42.4 MB) + 22 JPG (18.9 MB) + 9 SVG. `rose/border.png` 2.84 MB, `warrior/symbol_9.png` 2.50 MB (2550x1100), `jovious/bg.jpg` 3.43 MB. A lion rank-1 cert = parchment 1.69 + border 1.89 + symbol 0.24 = **3.83 MB**; warrior rank 9 = **4.60 MB**; jovious = **4.13 MB**.
  - Proposal: a build-time script emitting `foo.webp` beside each master, plus a `display` rendition at 850x1100 (96 dpi). `Scroll::ArtBase()` (`class.Scroll.php:403`) gains a size argument: the create-page preview and any bulk thumbnail take `display`; only `render` and `compose` take the 300 dpi master. Serve via `<picture>` or an nginx `try_files … .webp` map. Measured q88 WebP: `lion/border.png` 1.89 -> 0.51 MB (-73%), `rose/border.png` 2.84 -> 0.59 (-79%), `warrior/symbol_9.png` 2.50 -> 0.26 (**-90%**); PNG corpus -67%, whole corpus -51% at q85.
  - Why: the create page's live preview renders into a ~600px stage but downloads 300 dpi plates; every order change costs ~4 MB for a postcard-sized picture.
  - **Note on the existing pipeline:** `dc466607` (masters + WebP renditions) is on `feature/high-res-images`, **NOT merged here** — `grep -rl webp --include=*.php` finds only `orkservice/Map/charticon.php` on this branch. It also only covers UPLOADED heraldry, not static art. But it establishes the naming (`000123_display.webp`) and the `Size` argument on `GetHeraldryUrl`, and `ab9d09f9` already fixes "scroll builder must request master". `Model_Scrollery::heraldry_url():750` calls `GetHeraldryUrl` with NO `Size` — that will silently start delivering a 256px thumb into a 300 dpi certificate the day those branches meet. Worth a `'Size'=>'master'` now.
  - Effort: M — Risk: lossy WebP on line-art borders; spot-check at 300 dpi, or use lossless for the border layer (lossless lion/border = 1.28 MB, still -32%).

- **The shared border emits 48 KB of `<defs>` per certificate — the biggest markup win available**
  - Now: `scroll/_border.tpl` is 96,683 bytes: a `<defs>` block of **47,938 bytes** (32 `<symbol>`, 68 `<path>`) plus an optional ~47 KB griffon `<g>` (line 267) and 81 `<use>`. `custom.tpl:90`, `battle`, `griffon` and `dragon` (twice) compose it, **and `custom` is the generic fallback**. Real data: event 12250 is 391 awards, **391 of them `award_id` 94 (Custom Award)** — a 200-cert run there is 200 identical copies of that defs block, ~10 MB of inline SVG and ~6,400 duplicate element ids (also §3.3's dragon hazard, at scale).
  - Proposal: hoist the `<defs>` into a page-level hidden `<svg>` exactly as `_filters.tpl` already does — its header comment even states the rule ("Defined ONCE per page, not per certificate"). Each certificate then emits only its `<use>` list plus the per-order colour pair, which already live on the local `<svg>` root and keep working across documents.
  - Why: ~50 KB -> ~2 KB per certificate. On the worst real event that is 10 MB of HTML down to ~0.5 MB, and it removes the duplicate-id class of bug entirely.
  - Effort: M — Risk: must survive the create page's `mount.innerHTML = d.Html` replacement (`scrollery.js:381`), so the defs must be emitted by the PAGE, not the fragment.

- **`MAX_PRINT_RUN = 200` is far past where Chrome's print rasteriser gives up**
  - Now: `class.Scroll.php:24`, enforced at `controller.Scrollery.php:222` and again client-side (`Scrollery_bulk.tpl:280`). The docblock justifies it on QUERY cost, not raster cost.
  - Arithmetic: a 2550x3300 image decodes to **33.7 MB of RGBA**. A typical certificate stacks 2-4 DISTINCT full-page rasters. A 50-cert mixed run touches ~15-25 distinct plates = **500-840 MB of decoded bitmap** before compositing. Every `mix-blend-mode` layer (42 across the partials; lion alone stacks border x2 and symbol x2) forces its own stacking context and a backdrop read, so the rasteriser cannot draw straight through. Desktop Chrome renderer processes die in the low single-digit GB; **iOS Safari tabs are capped nearer 200-400 MB**, so mobile print fails well under 10.
  - Proposal: drop the practical cap to ~25 and chunk — "Print 91 certificates" opens runs of 25 sequentially, or better a paged render route (`&awards=…&page=2`) with a "Print next 25" control. Keep 200 as the hard server-side guard.
  - Why: the current failure is a hung tab or a half-blank print job with no error — discovered after the paper is gone.
  - Effort: M — Risk: more dialogs per run; mitigate by confirming once and stepping through.

- **`window.print()` failure modes — enumerated, with two verified as NON-issues**
  - **Verified safe:** every layer is an `<img>`, not a CSS background. `grep background scroll/*.tpl` finds one comment; `scrollery.css` has `background` only on the h1-h6 pill reset (`:79`). So Chrome's **"Background graphics" checkbox being off does NOT drop the parchment or borders** — and `print-color-adjust:exact` is set on `.award-template` (`:151`) and again in `@media print` (`:612`).
  - **Real, unhandled:** (a) **browser headers/footers are ON by default in Chrome/Edge** and will stamp the URL and date across a 0.125in margin (`scrollery.css:589-591`); nothing in the page can suppress them. (b) **Scale** — `@page{size:letter;margin:0.125in}` gives an 8.25x10.75in box; `.scroll-page` keeps `aspect-ratio:8.5/11`, so art lands at 8.25x10.68in, and most printers add another 0.16-0.25in unprintable area — a visible white frame on artwork designed full-bleed. (c) **Firefox** routes print through the platform backend and has a long history of flattening or dropping `mix-blend-mode`; the owl `filter:url(#OWL_edge-detect)` (`:440`) is an even likelier casualty. (d) **Safari** renders HTML inside `<foreignObject>` unreliably at print scale. (e) `image-resolution: 300dpi` (`Scrollery_render.tpl:45`) is implemented by no shipping browser — dead.
  - Proposal: a short, dismissible "Before you print" panel on the render page (Chrome recommended · uncheck Headers and footers · Margins None · Scale 100%), a `?margin=0` variant for borderless-capable printers, and one printed test per browser recorded in the deferred doc.
  - Effort: S — Risk: none; copy plus one CSS branch.

- **The PDF seam — the case, and the honest verdict on client-side**
  - **Client-side alternatives do NOT work.** `html2canvas` reimplements a subset of CSS and **has never supported `mix-blend-mode`** — it would flatten all 42 blends to normal alpha, i.e. print a DIFFERENT certificate. `satori` renders a JSX subset, supporting neither blend modes nor SVG filters. `foreignObject` -> `canvas.drawImage(svgImage)` is blocked outright: the SVG references cross-document `<img src>` and webfonts, which taints/blanks the canvas unless every asset is inlined as a data URI — ~4 MB of base64 per certificate, and STILL leaves Safari's foreignObject rasterisation broken. Verdict: no client-side path preserves fidelity.
  - **Server-side MVP:** one Node sidecar container, `puppeteer.launch()` reused across requests, `POST /scroll.pdf` taking the same `Scrollery/render` URL plus a short-lived signed token, `page.pdf({printBackground:true, preferCSSPageSize:true})`. Chrome is already the reference renderer, so fidelity is exact by construction. ~500 MB RAM idle, ~1.5-3s per certificate, one file, no PHP changes beyond the token.
  - **What it unlocks:** email the scroll to the recipient; archive a PDF on the award row so a reprint is a download not a re-render; hand a print shop a real PDF; **mobile output at all** (the only realistic path given the memory ceiling above); and bulk becomes a server job streaming one PDF instead of a 200-page browser document.
  - Effort: L — Risk: a new runtime in the deploy. This is the "concrete need" §2.5 parked for — mobile and email are it.

- **Caching: what is safe, and what must never be**
  - Now: nothing in `class.Scroll.php`, `model.Scrollery.php` or either controller touches `Ghettocache` (verified by grep), although the stack ships it and memcached runs in the container.
  - Safe: `Scroll::Orders()`/`Recipes()` (`:210`,`:155`) — pure file reads. `park_details()` is memoised per request (`:789`) but identical across every officer; a 1-hour Ghetto entry keyed on park id is free. Best of all, the **composed markup** keyed on `awards_id + variant + recipe-hash` — `Scroll::Render()` is a pure function of the award row, so a reprint of the same certificate is a cache hit. At ~50 KB per custom certificate that fits memcached's 1 MB item limit; **cache per CERTIFICATE, never per page** (a 200-cert page would exceed it and fail silently).
  - **Must never be cached:** `viewer_may_print()` (`:48`) and the bulk scope predicate. §4 records that this exact surface already leaked cross-tenant once; a cached authority decision keyed on anything but `(viewer, award)` re-opens it. Bust the markup cache on award edit/strip.
  - Why: `render()` loops `scroll_for_awards_id()` per id (`controller.Scrollery.php:225`), and each call runs `AwardsForPlayer()` (`:723`) AND `GetPlayer()` (`:52`) — a straight N+1 that at 200 ids is ~400+ domain queries against a 391k-row table before a single byte of HTML.
  - Effort: M — Risk: cache-key omissions; include the recipe and pronoun override or reprints diverge.

- **Batch the bulk render's award lookups** — `award_row()` fetches one award via `AwardsForPlayer(['MundaneId'=>0,'AwardsId'=>$id])` then loops the result to find it (`model.Scrollery.php:721-735`). An `AwardsForIds(array)` variant plus one `GetPlayers()` by the resulting mundane-id set would collapse ~400 queries to ~4. Effort: M — Risk: add the batch call rather than change the shared method.

- **Module chrome weight — the render route is right, the create page is not** — `Scrollery_render.tpl` loads only `scrollery.css` (19 KB) + 276 KB of fonts. The create page (`Scrollery_create.tpl:115-117, 462-471`) additionally pulls **`revised.css` 437 KB and `revised.js` 950 KB** for one autocomplete and `awInitPicker` — ~1.4 MB of CRM to render a preview. Not a Scrollery bug (it's the shared frontend bundle), but the module is a good candidate for the first page to take a trimmed subset. Effort: L (repo-wide project) — Risk: high; note it, don't do it here.
