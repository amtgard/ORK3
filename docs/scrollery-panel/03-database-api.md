# Panel report — Database Integration & API

## Summary
The query layer is honest about its own shape (the `…SqlForTest()` split is genuinely good, and the bulk predicate's scope fix is correct), but the module's single hottest read path is accidentally 200x more expensive than it needs to be, and that path now sits on the award-GRANT success handler as well. The bulk 200-row cap is applied to the wrong population at the wrong point in the pipeline, silently discarding 60% of a large court's certificates with no way to reach them. Permissions are fail-closed in the right direction but leave **120,284 award rows (30.7% of the corpus)** printable by nobody but the recipient — three orders of magnitude larger than deferred §3.12c's "four rows". "No new storage" is right for recipes and wrong for one thing: a print log. And the bare render route is a *page*, not a seam — a headless renderer has no way to authenticate to it.

## Findings

- **[BUG] `award_row()` fetches 3,076 rows through 8 LEFT JOINs to find one**
  - Now: `model.Scrollery.php:723` calls `AwardsForPlayer(['MundaneId'=>0,'AwardsId'=>$id])`. `class.Player.php:1155` appends that as `where awards.mundane_id='0' or awards.awards_id='N'` — an UNPARENTHESISED OR. There are **3,075 rows with `mundane_id=0`**, so every call returns 3,076 rows of ~40 columns, `SELECT DISTINCT` (EXPLAIN: `Using temporary`, `index_merge`), sorts by a 6-term ORDER BY, hydrates 3,076 x 27-key PHP arrays — then foreaches to keep one. Profiled: **36.2 ms** vs **0.18 ms** without the disjunct.
  - Proposal: give `AwardsForPlayer()` a real single-row branch — when `AwardsId` is valid and `MundaneId` is 0, emit `where awards.awards_id=N`. One `if`.
  - Why: `Scrollery/render` loops this per id up to `MAX_PRINT_RUN=200` (`controller.Scrollery.php:226`) => **~7.2s of DB time and 615,200 discarded PHP arrays** for a 200-scroll run before any markup. Worse, `Controller_Award::handle_success()` (`controller.Award.php:126`) now runs it on **every award grant** — the ORK's hottest officer workflow. Scrollery made award entry measurably slower.
  - Effort: S — Risk: `AwardsForPlayer()` is shared; the `or` is load-bearing only for callers passing both a real MundaneId AND an AwardsId — grep says none do. Pin with a test.

- **[BUG] The bulk 200-cap is applied before the art filter, after an alphabetical sort**
  - Now: `bulkSqlForTest()` ends `order by m.persona, a.name, awards.rank limit 201` (`model.Scrollery.php:382`); `awards_for_bulk()` splits into Printable/Excluded in PHP (`:479`).
  - Data: event 12250 / kingdom 4 is **495 rows, all 495 printable** (415 distinct recipients). The officer gets the alphabetically-first 200; 295 certificates unreachable — the date filter's finest grain is one day and this IS one day. **24 event/kingdom pairs exceed the cap**; worst is event 8462/kingdom 4 at **741** (541 lost). Deferred §3.12b understates both the count and that the loss is ALPHABETICAL — it always eats the same recipients.
  - Proposal: (1) return a `Total` count so the banner says "200 of 495". (2) Keyset paging `&after=<persona>` on the same ORDER BY + a "Print the next 200" control. No new storage. Optionally push officer_role/dangling exclusion into the WHERE so the cap counts printable rows only.
  - Why: bulk print for a coronation court is the flagship officer use case, and it is exactly where it fails — silently, in favour of recipients whose personas start with A.
  - Effort: M — Risk: keyset paging on non-unique `m.persona` needs `awards_id` as tiebreaker in both ORDER BY and cursor.

- **120,284 award rows printable by nobody but the recipient — including ORK admins**
  - Now: `model.Scrollery.php:694` grants on recipient identity, AUTH_EDIT on `ParkId` (=`at_park_id`), or AUTH_EDIT on `KingdomId` (=`at_kingdom_id`). Failure is a silent `header('Location: '.UIR.'Scrollery')` (`controller.Scrollery.php:234`).
  - Data: `at_park_id=0 AND at_kingdom_id=0` is **120,284 rows, 30.7% of 391,296**, of which **119,917 have art**. NOT historical debt: 2,080 in 2023, 1,973 in 2024, 1,929 in 2025 — ~6.5% of current grants, because `Controller_Award::add_award()` (`controller.Award.php:117`) defaults ParkId/KingdomId to 0 when the form leaves "where given" blank. Separately **1,616 rows** have `at_park_id>0` with no `at_kingdom_id`, invisible to the kingdom officer.
  - Proposal: (a) add an AUTH_ADMIN branch — fixes awards_id 13/119/120/3575 by itself. (b) when both scope ids are 0, fall back to `ork_awards.park_id`/`kingdom_id`, which already sit on the row and record the recipient's HOME at grant time — no new joins. (c) replace the silent redirect with a denial page explaining it. Separately nudge the grant form: a scroll printed from `Scrollery/create` today can be un-reprintable tomorrow because the officer left "where" blank.
  - Effort: S for (a)+(c), M for (b) — Risk: (b) is a genuine widening — get it decided, not inferred.

- **The render route is a page, not a seam — a PDF service cannot authenticate to it**
  - Now: `render()` and `compose()` re-check against `$this->session->user_id` (`controller.Scrollery.php:210`, `:257`). "Shareable" only to someone already holding that officer's cookie. `Scrollery_render.tpl` is bare HTML with no machine-readable envelope.
  - Proposal: (1) a short-lived signed print token `?awards=…&t=<hmac(awards|viewerId|exp, APP_SECRET)>` minted by the page that already passed the check, accepted by `render()` IN PLACE OF the session — what a headless Chrome fetch actually needs. (2) a `Scrollery/manifest` GET returning `{scrolls:[{awardsId,order,rank,title,player,date,issuer,variant,recipe}]}` — `BuildScroll()` output minus markup — so a renderer/archiver/mail-merge consumes DATA without scraping SVG. (3) `Cache-Control: private, no-store` on `render_bare()` (`:350`), which currently sets only Content-Type.
  - Why: §2.5 parks server-side PDF on "the bare render route is already the seam". It isn't yet — the auth model is the missing half, and it is the cheap half.
  - Effort: M — Risk: token expiry/single-use semantics; scope the HMAC to the exact id list so it cannot be widened.

- **Storage: say NO to saved recipes, YES to a print log**
  - Against storage for recipes: a recipe is five closed-vocabulary tokens fully reconstructible from the compose URL; `Scroll::NormaliseRecipe()` (`class.Scroll.php:171`) already rejects everything outside the vocabulary, so a URL IS the saved recipe. A per-kingdom default look is §2.4 CLOSED with data behind it. Don't reopen either.
  - For a print log — different in kind, it records an EVENT not a preference. `ork_scroll_print (scroll_print_id, awards_id NULL, mundane_id, printed_by_id, scope_type, scope_id, order_id, rank, variant, recipe_json, printed_at)`. Answers four questions nothing else can: *did this player already get a scroll?* (the recurring court question), *reprint exactly as printed in 2019* (variant+recipe are per-print and currently unrecoverable), *how much is the module used?* (feeds the existing Release Feature Utilization report), *who printed 741 certificates at 3am*. One insert per render, no read on the hot loop.
  - Migration: `db-migrations/2026-09-05-scroll-print-log.sql`, InnoDB, `key(awards_id)`, `key(printed_at)`, `key(mundane_id,printed_at)`. Must be classified in ork-db's `migration-classification.json5` or `drift-check --strict` blocks the whole unit-test run.
  - Effort: M — Risk: insert-on-GET means refresh double-logs; dedupe on `(awards_id, printed_by_id, within 60s)` or log from a `sendBeacon` on `afterprint`.

- **Compose's GET payload is unbounded and the API contract is ad hoc**
  - Now: `scrollery.js:555-574` packs 20 fields into a query string and `window.open`s `Scrollery/compose&…`. `reason` comes from a textarea with **no `maxlength`** (`Scrollery_create.tpl:322`) while the column is `varchar(400)`. A pasted citation blows past nginx's request-line buffer (414, no useful error). `ScrolleryAjax::preview()` returns `{'Status':{'Status':1|5,'Error':…},'Html':…}` at HTTP 200 for every outcome, POST-only.
  - Proposal: `maxlength="400"` + server-side `mb_substr(…,0,400)` in `compose()` and `preview()`. Make `preview` accept GET as well as POST — it is a pure read, and a GET-able preview is trivially curl-testable, cacheable, shareable. Keep the `Status` envelope but set real HTTP codes (401/403/422) alongside. `exit;` after `echo json_encode` is correctly observed at `:26/:39/:64/:111` — good.
  - Effort: S — Risk: none; read `$_POST + $_GET` explicitly, not `$_REQUEST`.

- **Indexes the bulk path wants** — `ork_awards` has single-column `at_kingdom_id`/`at_park_id`/`at_event_id`, no date composite. Kingdom date-range bulk on kingdom 10 (**22,841 rows**) does `ref` then `Using temporary; Using filesort` — 24ms today, fine, but degrades linearly and the events picker does the same `group by` over the same span. Composite `(at_kingdom_id,date)` and `(at_park_id,date)` turn both into narrow range scans. Effort: S.

- **Integration surface worth taking: Court Planner** — Court Planner stages grants then commits on Finalize. That finalize step is the exact moment a court's `awards_id` list exists as a SET — precisely the input `Scrollery/render?awards=…` wants, and precisely the set the 200-cap mangles when reconstructed after the fact from an event id. A "Print this court's scrolls" button on the finalize result, carrying the ids it just wrote, sidesteps the bulk query entirely for the highest-volume real case. Effort: M — Risk: court sizes exceed 200 (event 12250 = 495), needs the paging work first or a chunked link set.
